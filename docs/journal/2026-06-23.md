### Load-bearing: takeover is one-shot, deliberately NOT persisted
`env_core.ManagedServe` is persisted as desired state and **restored/re-applied on daemon restart** (and re-run on serve retry). So takeover must NOT live there — it would re-evict on every restart. It's applied once from `req.Takeover` in `EnsureServe`, before the serve attempt. `tunnelController.Takeover(env, name)` resolves the tunnel by name (`ScopeOwned`) and **no-ops if the tunnel doesn't exist yet** (nothing to take over; the serve flow then creates it). The foreground CLI path is naturally one-shot (single invocation) and calls takeover only when the tunnel pre-existed (`!create`).

## Live validation against dev controller :18081 (Phase 1) — found + fixed a real bug
Validating end-to-end against real OpenZiti (edge mgmt API at https://localhost:1280, admin/admin; no `ziti` CLI). Clean-slate fabric. Passed on the real fabric: standalone tunnel created with **NULL env_id**; bind policy `<svc>-bind` with `identityRoles=["#agora-account:<id>"]` (account role, not env identity); serve from env A creates a terminator; **serve from a second env of the same account succeeds** (account bind lets it bind).

**BUG (fixed): retire handler's terminator eviction used an invalid OpenZiti filter.** `agora disable` returned a controller 500 and left the env `enabled` + serve record `active`. Cause: `EvictTerminatorsByIdentity` filtered terminators by `identity="<id>"`, but **OpenZiti terminators are not filterable by `identity`** (`400 INVALID_FILTER: unknown symbol 'identity'`; the `identity` field is empty for edge-bound terminators). This is exactly the work order's finding **R2-A2**, which I'd missed. Fix: filter by **`hostId`** instead — it *is* server-side filterable (200) and equals the binding identity's id (verified: `hostId=<envZitiId>` matched that env's terminator). One-line change in `automation/tunnel.go`; rebuilt, unit tests still green. **The takeover path is unaffected** — it filters by `service="<id>"`, which OpenZiti accepts (200).

**Fabric facts for future work:**
- terminator filterable fields: `service`, `service.name`, `router`, `router.name`, `hostId`, `address`, `id`, `binding`, `tags`, … — **NOT `identity`**. Filter a tunnel's host terminators by `hostId="<env ziti identity id>"`; filter a service's terminators by `service="<ziti service id>"`.
- `kill -9` on a foreground serve **drops its terminator immediately** (edge-bound terminators are connection-tied). So the "wedged but still hosting" state that takeover uniquely solves is NOT reproducible by killing the process — it needs a host that stays connected but stops serving. Relevant to Phase 2.

**BUG 2 (fixed): a retired environment's serve record on a standalone tunnel lingered `active`.** After the hostId fix, retire-while-hosting succeeded (no 500), terminator evicted, tunnel survived — but the env's `tunnel_serves` row on the standalone tunnel stayed `active`. Root cause is the same wrong assumption as bug 1: the work order's grounding said the serve records "cascade-clear via the tunnel_serves env FK when the env row is deleted," but **`Environments.Delete` is a soft delete**, so the `ON DELETE CASCADE` never fires, and the retire handler's serve loop only iterates `ListByEnvironment` = session tunnels (never standalone). Consequence: the lingering `active` record blocks re-serve from another environment (unique-active constraint) until the reaper stales it ~60s later. Fix: new `TunnelServes.DisconnectAndDeleteByEnvironment` (mark active→disconnected + soft-delete all the env's serve records, keyed by environment), called in `disableEnvironment` before the env soft-delete. This is a **DB-only fix** (no fabric), fully validated by a testcontainer integration test (`TestRetireClearsServeRecordOnStandaloneTunnel`); the work order had marked this cleanup "optional polish," but it's load-bearing.

**Regression guards added** (would have caught both bugs): `automation.TestEvictTerminatorsUsesCorrectFilters` pins the filter strings (`service="..."` / `hostId="..."`); `controller.TestRetireClearsServeRecordOnStandaloneTunnel` covers the serve-record cleanup.
